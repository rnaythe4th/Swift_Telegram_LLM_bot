# Задания для агентов по внедрению DeepSeek Web

Прочитай [архитектуру](deepseek-web-architecture.md) и актуальное описание приложения в [.claude/CLAUDE.md](../.claude/CLAUDE.md). Работа идёт в `LLM_chat_bot`. Используй `Ai-news-bot` как локальный источник браузерного кода, тестов и инструкции входа. Начинай с имитатора. Существенные проверки живого аккаунта выполняй в выделенном тестовом окружении с владельцем профиля и синтетическими сообщениями.

## Порядок работы

Координатор согласует версию локального контракта и формы событий с агентами браузера и Swift до изменения портов. Пробу деплоя, браузерный обработчик и модель Web-состояния можно разрабатывать параллельно в разных ветках или worktree. Агент Swift владеет `Sources/`, Swift-тестами и подключением настроек. Агент браузера владеет отдельным каталогом браузерной службы и её тестами. Агент деплоя владеет Dockerfile, стартом процессов и runbook. Интеграционный агент объединяет изменения и проверяет полные сценарии после стабилизации контракта. Сохрани имеющиеся изменения пользователя в рабочем дереве.

## 1. Агент деплоя

**Задание.** Подтверди работу одного Firefox в текущем образе и подготовь удалённую авторизацию с Mac. Используй существующие базовый образ, процесс Swift и `/ready`. Артефакты этапа — измерения, воспроизводимая конфигурация и инструкция входа.

**Локальный замер.** Linux ARM64 в Docker Desktop, `swift:6.2-bookworm-slim`, Firefox ESR 153.7.0, geckodriver 0.36.0, UID 65532, один vCPU, RAM и RAM+swap ограничены одинаково. В каждом прогоне WebDriver сначала открыл локальную HTML-страницу в Firefox с окном, VNC ответил на loopback, затем новый процесс Firefox прочитал постоянную cookie из того же профиля в headless. Swift и сайт DeepSeek в пробе отсутствовали. Размер профиля после прогона составил 52 МиБ. Firefox вывел `CanCreateUserNamespace() clone() failure: EPERM` при проверке версии. Оба режима запустились с обычными настройками контейнера. На целевом deployment проверка песочницы остаётся обязательной.

| Лимит памяти | `memory.current` с окном и VNC | `memory.current` headless | `memory.peak` | OOM |
| --- | --- | --- | --- | --- |
| 512 МиБ | 424 МиБ | 374 МиБ | 437 МиБ | 0 |
| 1 ГиБ | 401 МиБ | 367 МиБ | 431 МиБ | 0 |

1. Собери пробу от `swift:6.2-bookworm-slim` под архитектуру целевого deployment с Firefox ESR, закреплённым geckodriver, Python и Xvfb/x11vnc. Проверь старт под UID 65532 с обычными ограничениями контейнера. Проверь читаемый и записываемый профиль после перезапуска, сохранённую авторизацию и эксклюзивное владение. Проверь реальные значения `/dev/shm`, cgroup и sandbox на Railway. Если платформа ограничивает отдельные механизмы песочницы, запиши диагностический вывод и проверь поведение Firefox без снятия штатных защит.
2. На staging с полным образом Swift и браузерного обработчика проверь ограничение RAM и CPU текущей реплики, том, архитектуру и доступ к `chat.deepseek.com` из выбранного региона. Собери базовый профиль Swift, headless в простое, серию обычных ходов, длинный диалог, завершение одного запроса и начало другого, ручной вход через Xvfb и перезапуск. Сними `memory.current`, `memory.peak`, `memory.events`, CPU, занимаемый профиль, размер образа, время старта и p95 времени хода. Для p95 используй серию запросов к локальному имитатору. Живые вызовы выполняй в пределах квоты владельца. Прикинь месячную стоимость для измеренной нагрузки, включая Postgres. Фиксируй длительность и выборку, чтобы данные можно было повторить.
3. Собери runtime с двумя управляемыми процессами. Проверь запуск API-режима без браузера, ограниченное завершение по `SIGTERM`, недоступность Web при незапущенном worker, сохранение работы `/ready`, потерю writer lock и восстановление webhook после redeploy с томом. Worker слушает loopback и защищён отдельным токеном. Firefox и графические процессы работают от непривилегированного пользователя. Создай `/tmp/.X11-unix` с правами `1777` от `root` при сборке, чтобы Xvfb мог открыть сокет под UID приложения. Проверь права каталога профиля после каждого монтирования.
4. Подготовь команды обслуживания Web и документируй обычный вход, повторный вход и смену аккаунта. Испытай временный Xvfb с Xauthority, парольный VNC на loopback, `ssh -L` с Mac, прозрачно видимый статус ожидания для Telegram, очистку сеанса по завершении, таймауту или сбою и возврат в headless. Для удалённого входа используй процесс входа из справочного бота как ориентир. [Вход через Firefox в Ai-news-bot](../../../Ai/Ai-news-bot/deploy/android/README.md#ручной-вход-в-deepseek-web) · [Railway SSH](https://docs.railway.com/cli/ssh#forward-a-port-with-ssh--l)

**Приёмка.** Измеренная пиковая память полного сервиса и размер профиля имеют запас под фактический лимит, нет OOM, длительного CPU throttling, потерянной авторизации или параллельного открытия профиля. Ориентир для первого замера — минимум 25% запаса по памяти на худшем наблюдавшемся сценарии. Повторный контрольный запрос проходит после закрытия туннеля и redeploy. Если критерии не выполнены, приложи измерения и точную причину для решения владельца.

## 2. Агент браузерного обработчика

**Задание.** Адаптируй переносимые части Firefox/Selenium из Ai-news-bot к длительным диалогам. Используй закреплённые зависимости, приватный профиль с файловой блокировкой, один активный браузерный ход и явно ограниченные операции. [Референс браузерной службы](../../../Ai/Ai-news-bot/ainews/browser.py) · [Референс тестов](../../../Ai/Ai-news-bot/tests/test_model_browser.py)

1. Согласуй с агентом Swift контракт `v1`. Подготовка получает ID операции, аккаунт, ожидаемый ID диалога или действие создания и ожидаемый последний ход. Она резервирует рабочую вкладку на ограниченное время. Отправка использует ту же операцию и один промпт после подтверждения Swift. Состояние операции различает «не отправлен», «отправка могла произойти», «пользовательский ход подтверждён», «финальный ответ подтверждён» и типизированные ошибки. Возвращай новый канонический ID, как только его можно подтвердить, и описание последней позиции. Поддержи отмену и получение состояния без повторного клика. Повторный ID возвращает известное состояние, включая после потери соединения в рамках живого worker. Восстановление после рестарта начинается с durable intent на стороне Swift.
2. Раздели навигацию, проверку страницы, отправку и чтение финального текста. Для существующего диалога валидируй точное соответствие ID, origin и ожидаемого хвоста. Для нового проверь состояние пустого composer. Перед кликом запомни состояние сообщений. После клика дождись нового пользовательского хода и финального состояния именно его ответа. Проверь условия окончания на каждом поддерживаемом режиме. Владелец вкладки сохраняет её, пока операция не завершилась, не остановилась или браузер не был закрыт. При подтверждённой ручной проверке поставь Web на паузу.
3. Разнеси категории квоты, входа, временной перегрузки, длины ввода, недоступного или переполненного диалога, изменения UI, отмены и неопределённого результата. Распознавай подтверждённое состояние UI текущей операции. Сохраняй смысл обычного текста ответа даже при наличии слова «лимит» внутри него. Селекторы, правила навигации и настройки браузера остаются внутренними для worker.
4. Добавь локальную страницу со старыми ответами, двумя именованными диалогами, созданием нового ID после первого вопроса и имитацией предельных ошибок. Используй её в тестах авторизации HTTP, блокировки профиля, таймаута до и после клика, повторного запроса статуса, неожиданного URL и захвата именно нового ответа. Проверь, что второй запрос не стартует до подтверждённой остановки первого.

**Приёмка.** Два хода в A и один ход в B дают нужные ID и финальные ответы. При возвращении в A используется старый ID и новый ответ. Без входа, при квоте и при неоднозначной отправке контракт выдаёт разные статусы. Тесты работают на локальной странице без аккаунта DeepSeek.

## 3. Агент Swift

**Задание.** Включи `deepseek-web` в штатные пути Telegram, реализуй durable-привязку и точную прослушку. Начни тестами с фальшивым worker и `FakeTelegram`.

1. Обнови `ServiceProvider`, реестр, `AppConfig` и `AppAssembly`. Проверь `CaseIterable`, парсинг, обработку выбора сервиса в командах и меню, дефолты из домена, админские пресеты, режимы и OpenRouter price monitor. Выбор через несуществующий адаптер отклоняй до изменения настроек. При инсталляции только с Web проверь отсутствие исходящих вызовов API-провайдеров. При отключении Web отобрази статус сохранённого выбора и дай оператору сменить сервис. [Типы](../Sources/LLM_chat_bot/Domain/Providers/ProviderTypes.swift) · [Команды](../Sources/LLM_chat_bot/Application/Commands/BotCommandHandler+ChatSettings.swift) · [Меню](../Sources/LLM_chat_bot/Application/Menu/BotMenuHandler+ChatSettings.swift)
2. Введи необязательное Web-состояние в снимок контекста, реализацию подтверждённого checkpoint, сериализацию переходов, отметки повторной доставки и восстановление незавершённой операции. Покрой миграцию группы, отсутствие Web-поля в старой строке, перезапуск после разных стадий, `/forget`, retention и выход из writer lock. Проверь порядок записей общего write-behind на тестовой Postgres. [Состояние](../Sources/LLM_chat_bot/Domain/Chat/ChatContextStore+ChatContext.swift) · [Постоянное хранилище](../Sources/LLM_chat_bot/Infrastructure/Persistence/PostgresStatePersistence.swift)
3. Проведи Web-генерацию через общий вход для сообщения и примера с кнопки. Вводи отдельную очередь до общего лимитера, сохраняй ID Telegram-источника, сверяй эпоху перед отправкой и фиксацией. Реализуй отмену и раздельные дедлайны ожидания очереди, браузерной подготовки и генерации. После неоднозначного сбоя запроса отправки опрашивай состояние операции, отключив транспортный авторетрай отправки. Событие `.text` публикуй только после подтверждённого финала. Согласуй deadline и keep-alive с текущим `StreamWatchdog` (75 секунд тишины, 600 секунд всего). Таймер очереди должен завершаться отдельным сообщением. [Координатор](../Sources/LLM_chat_bot/Application/Generation/GenerationCoordinator.swift) · [StreamWatchdog](../Sources/LLM_chat_bot/Application/Generation/StreamWatchdog.swift)
4. Сделай единый путь для команды и кнопки по ролям, истории и прослушке. Сохрани эффективный текст роли. Строитель промпта принимает структурированные реплики с проверенной границей и собирает ограниченный ввод. Исключай текущий вопрос и нативные дубликаты. Положи лимиты, обработку reply, поведение после очистки и ротацию в тесты. Уточни надписи `/history`, `/historylength`, `/forget` и меню прослушки. Существующие права изменения общего чата действуют для Web, а доступ к роли и Web-прослушке не требует платного тарифа. [Прослушка](../Sources/LLM_chat_bot/Application/Commands/BotCommandHandler+Listen.swift) · [Меню прослушки](../Sources/LLM_chat_bot/Application/Menu/BotMenuHandler+Listen.swift)
5. Разведи информационные ответы «квота», «подождите», «попросите админа войти» и остальные ошибки. Для draft и edit используй общий перевод категорий. Пауза аккаунта переживает рестарт. У ошибки Web нет assistant turn, расхода денег, расхода премиум-единицы или замены сохранённой модели. Для успешного ответа адаптируй футер к доступным данным и проверь существующий путь разбиения Telegram. [Ошибки](../Sources/LLM_chat_bot/Application/UserFacingError.swift) · [Доставка](../Sources/LLM_chat_bot/Application/Generation/GenerationCoordinator+Streaming.swift)

**Приёмка.** `swift test` зелёный, тесты Postgres выполнены с `TEST_DATABASE_URL` на отдельной тестовой БД, новый `deepseek-web` выбирается на штатных входах, а API-настройки и их прежние правила оплаты проходят регрессию.

## 4. Интеграционный агент

**Задание.** Проведи сквозную приёмку на имитаторе. После прохождения staging-критериев выполни ограниченный пилот с владельцем. Для каждой проверки запиши ожидаемый результат, фактическое наблюдение и окружение.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Перемежающиеся вопросы в топиках A и B, General и двух личках, повтор после перезапуска | Каждая переписка сохраняет свой ID и контекст. Ответ и служебные сообщения приходят в исходный топик. |
| Нейтральная роль, грубый пресет, разговорно-матный пресет, смена через меню и `/setrole` | Имитатор фиксирует точную эффективную роль и отдельный вопрос. В живой проверке фиксируется реально полученный стиль или отказ. Новая роль открывает новый диалог. |
| Фоновая реплика, reply на неё, затем ещё две реплики между вопросом и ответом | Запросы идут только на обращения. Цитаты подписаны, вопрос встречается один раз, следующие реплики приходят один раз в следующем запросе. |
| Много реплик, длинная роль и вопрос, кириллица и emoji | Предел рассчитан после сборки. Старые фоновые строки уступают место вопросу и роли. Для слишком длинной обязательной части показывается сообщение. |
| Кнопка и `/clear_history` во время очереди, отправки и готового ответа, затем reply на старую реплику | Представление нового диалога пустое до свежего хода. Нет старого ответа, старого pre-roll и восстановленной привязки. Соседние топики продолжают свои диалоги. |
| `/listen off`, `/listen clear`, повторное включение и `/forget` | Текущая память учитывает каждое действие. Ответы, полученные с участием стёртых реплик, не возвращаются в bootstrap. `/forget` удаляет локальный контекст и описывает удалённое хранение. |
| Переполнение, ручное удаление диалога, изменение последнего хода извне, смена аккаунта | Продолжение идёт только в проверенном диалоге. Ротация переносит ограниченный допустимый хвост. Смена аккаунта начинает с чистой привязки. |
| Квота до и после возможной отправки, перегрузка и обычный ответ со словом «лимит» | Квота даёт одно сообщение в draft и edit, новая попытка блокируется до паузы. Перегрузка и настоящий ответ идут по своим путям. Ход с ошибкой не меняет баланс и премиум-счётчик. |
| Два одновременных чата, кнопка «Стоп», разрыв HTTP, падение Postgres, процесс завершён после клика | Браузер сохраняет одного владельца. Клик возможен после подтверждения записи в БД. Восстановление сверяет операцию без дубликата. Команды и API-провайдеры доступны при ожидании Web. |
| Повторное Telegram Update, включая после `/forget` и рестарта, затем два новых Update с одинаковым текстом | Повтор события с живым контекстом использует прежнюю операцию, удалённый контекст остаётся удалённым. Два новых сообщения создают два отдельных хода. |
| Таймаут Telegram после подтверждённого веб-ответа | Сверка сохраняет подтверждённый ход в DeepSeek. Правка известного Telegram ID допускает повтор. Для новой отправки с неизвестным исходом фиксируется неопределённое состояние. |
| Вход с Mac, выключение Mac, redeploy | Авторизованный профиль переживает redeploy, штатный ход проходит headless, временный доступ закрыт. |

Дай владельцу итог по четырём вопросам. Укажи, сохранён ли контекст после redeploy, какие роли реально соблюдены, как проявляется подтверждённая квота и каковы измеренные ресурсы и стоимость Railway. Для живых проверок используй синтетические данные и возврати флаг в исходное положение после пилота, если постоянное включение не согласовано.
